# Empirical Code Security Framework: Methodology Documentation

## 1. Core Evaluation Methodology (`METHODOLOGY_OVERVIEW.md`)

This document establishes the empirical evaluation framework used to contrast the security posture of AI-generated pull requests against human-authored pull requests. By leveraging automated, high-throughput static analysis pipeline architectures, this methodology ensures scientific rigor, reproducibility, and elimination of evaluation bias.

### 1.1 Sampling Strategy and Dataset Selection
The evaluation matrix draws from the standardized **`AIDev-Pop`** dataset pool. To conduct a perfectly balanced 1:1 empirical comparison, a strict matching strategy was deployed:
* **AI Track Population:** 1,000 pull requests completely generated by autonomous AI developer agents.
* **Human Track Population:** 1,000 pull requests authored by human contributors, extracted from identical source repositories or matching difficulty domains to isolate behavioral variables.
* **Total Evaluation Volume:** 2,000 total pull requests spanning across identical target languages, repository star brackets, and code scale frameworks.

### 1.2 The Chunk-Based Batch Process (4x250 Execution Loop)
To counter API rate limit boundaries, prevent standard runner timeout exceptions, and ensure linear memory profiles during heavy static analysis evaluation, a **Sequential Chunking Protocol** was introduced:
* **Batch Slicing:** The 1,000 pull requests in each track are split into 4 distinct, sequentially isolated chunks containing **exactly 250 pull requests** each.
* **The Scanning Loop:** The automation orchestrator executes an iteration loop that processes these chunks one by one.
* **State Isolation:** Each chunk of 250 pull requests undergoes isolated checkouts, environment mapping, configuration caching, and error handling before advancing to the next batch.
* **Data Persistence:** The database dumps intermediate scanning telemetry at the boundaries of each chunk, preventing data loss in the event of a network disruption.

## 2. Automated Static Analysis Pipeline (`CODEQL_SCANNING_PIPELINE.md`)

This technical blueprint documents the automated continuous integration scanning pipeline configured to evaluate code changes.

### 2.1 CodeQL Pipeline Execution Lifecycle
For every single pull request pulled into the processing engine via the 250-item chunk loop, the platform carries out a strict execution sequence:
1. **Dynamic Workspace Checkout:** Cleans the workspace environment and checks out the specific target branch code modified by that particular pull request.
2. **Database Initialization (`codeql database create`):** Builds a structural CodeQL parsing database matching the repository's native programming language.
3. **Query Engine Analysis Execution (`codeql database analyze`):** Runs comprehensive rule matrices against the target database, pulling from the default security suites.
4. **Telemetry Artifact Export:** Extracts findings into standardized SARIF (Static Analysis Results Interchange Format) datasets.

### 2.2 Telemetry Parsing Metrics
The parsing pipeline extracts and indexes specific metadata keys into the central database:
* **Target Coordinates:** Exact relative file paths and code lines identifying where a defect lives.
* **Rule Definitions:** Triggering CodeQL rule IDs mapped directly to standard Common Weakness Enumeration (**CWE**) registries.
* **Severity Classifications:** Normalization of vulnerability tiers categorized cleanly into Critical, High, Medium, or Low impact classes.

### 3.2 Cross-Track Dismissal and Status Matrix
A core focus of this evaluation involves documenting post-scan lifecycle states across tracks:
* **Active Status:** Confirmed security flaws that require patching or represent active risk.
* **Dismissed Status (False Positives / Risk Accepted):** CodeQL alerts that were intentionally suppressed, signaling differences in code style patterns between human software engineers and AI code agents.
* **Volumetric Weighting:** Merging repository popularity metrics (star counts) to see if code security posture changes depending on the open-source community size.
